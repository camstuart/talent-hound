## Context

Every previous phase could be wrong in private. This one cannot: a query leaves the machine, reaches a third party, and is logged there. So the design question is not "how do we search" — it is "what is the smallest, most inspectable thing we can send, and how does the recruiter know exactly what it was".

## Goals / Non-Goals

**Goals:**
- A query that cannot carry a direct identifier by accident.
- A preview that is the request, byte for byte, not a rendering of it.
- An audit trail that proves a disclosure happened without becoming a second copy of what was disclosed.
- One role per listing, however many times it is found.
- Source respect that is deny-by-default rather than best-effort.

**Non-Goals:**
- No browser automation, now or as an option. The PRD forbids it and there is no flag.
- No company, profile, or news search. Role listings only.
- No shortlist. Phase 15 ranks what this phase finds.
- No cloud consent flow. Exa has its own per-query confirmation, which this phase implements; Phase 18 owns cloud model consent, which is a different thing.

## Decisions

### The preview is the request

`Preview` returns the exact query string. `Send` takes that string and transmits it unchanged. There is no post-processing between them, no template applied at send time, and no server-side rewriting.

This sounds obvious and is the thing most systems get wrong. A preview generated by one code path and a request built by another will diverge — usually the day someone adds a default filter — and the recruiter's confirmation will have been about something that was not sent. The test asserts byte equality between what the preview returned and what the fake server received, because that is the only assertion that stays true when someone adds the filter.

### Scrubbing is deny-by-default within the query builder, and advisory in the editor

The builder never emits a direct identifier: it draws from approved professional aspects and criteria, and it runs the scrubber over the result. Organizations are generalized — "Northwind" becomes the shape of the thing rather than its name — because a candidate's employer identifies them almost as well as their name in a small market.

The editor is different. A recruiter may deliberately type a company name, because searching "roles at Northwind" is a legitimate thing to want. So the editor warns rather than refuses, and warns *additionally* when what was re-added looks like a direct identifier. The asymmetry matches Phase 13's: automatic behaviour is conservative, deliberate human action is permitted and visible.

*ponytail: generalization is a word-list of organizational suffixes plus the capitalized-token heuristic, run over aspect wording. It over-generalizes some ordinary nouns, which costs recall on a query the recruiter can edit — the failure direction that is visible.*

### A cancelled preview leaves no trace of any kind

No request, no audit event, no search record. Cancellation is the absence of the operation rather than a recorded decision not to proceed.

An audit event for a search that did not happen would be a record of a disclosure that did not occur, which makes the audit log wrong in the one direction that matters — it would suggest the candidate's information went somewhere it did not.

### The audit event records that, not what

A disclosure event carries a timestamp, the provider, the task, the information categories, the initiative, and nullable record references. It does not carry the query, any result, or any content.

The search record carries the visible query, inside the owning initiative, because reproducibility needs it and the initiative is where the recruiter already has that information. The audit log is the thing that might be exported, reviewed, or retained longest, and a query in it is a candidate's professional shape sitting in the compliance artifact forever. Two records, two lifetimes, one deliberate separation.

### Identity resolves by precedence, and the precedence is total

Source ID, then canonical URL, then content fingerprint. The first that matches wins, and the order never varies.

Precedence rather than scoring because the failure mode of a scored match is two roles that are the same or one role that is two, discovered weeks later when a match cites the wrong listing. A fixed order is boring, explicable to a recruiter, and testable exhaustively — which is what the fixtures do, including the case where source ID and canonical URL disagree.

### A source observation is about content, not about time

Re-finding a role compares the content fingerprint. Same hash: nothing new happened, so `retrieved_at` moves and no artifact is created. Different hash: the listing changed, so a new immutable current source artifact is created, the previous link becomes historical, and everything derived goes Stale.

Historical artifacts stay visible and leave current retrieval. That is the whole reason artifacts are immutable: a match made in March cited the March listing, and the March listing has to still exist for that citation to resolve, even though the June listing is what matters now.

### Staleness is computed from a clock the caller supplies

Thirty days since retrieval, or past the closing date, means Stale. The comparison uses an injected clock, so the boundary cases are tests rather than a wait.

Rediscovery moves Stale back to Active, because the listing is demonstrably still there.

### Direct fetching is deny-by-default and the allowlist ships empty

`Fetch` consults an allowlist that contains nothing. Every host is refused, including ones that would obviously be fine, because the PRD requires an access review before a source goes on it and no review has happened.

Shipping it empty rather than shipping it absent is deliberate: an absent mechanism gets added later by someone who does not know the rule, while an empty one with a refusal message and a test is a mechanism whose rule is written down. SEEK and LinkedIn are additionally named in a permanent denylist, so adding them to the allowlist is not sufficient to enable them.

### Manual paste does not claim automated provenance

Content the recruiter pastes is stored as an artifact whose source says a person pasted it. It is not marked as retrieved from the listing, because nothing verified that it was.

## Risks / Trade-offs

- **Generalization loses recall.** A query that will not say "Northwind" finds fewer Northwind roles. The recruiter can add it back, deliberately, with a warning — which is the trade the PRD asks for.
- **The scrubber is a heuristic.** It cannot catch an identifier the recruiter types into the editor in an unexpected form; it warns on what it recognises and the preview is the real control.
- **The empty allowlist means Exa content or nothing.** When Exa's text is thin, the recruiter pastes. That is slower and it is the honest option.
- **Content fingerprinting treats trivial changes as changes.** A listing that re-renders with a different timestamp produces a new artifact. Normalizing harder risks missing a real edit, and the cost of the conservative direction is disk.
